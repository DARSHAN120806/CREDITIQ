# CreditIQ Application Validation Against Supabase

Date: 2026-10-07  
Mode: `RESEARCH_ONLY`  
`release_ready=false`

## Outcome

Supabase was reached through the configured application runtime connection and served
successful transactional API reads and writes. PostgreSQL reported version **17.11** and
Alembic revision **20261003_0003**. The application API smoke exercised authentication,
session rotation/revocation, application submission, prediction retrieval, history, and
admin read-only endpoints. The synthetic application writes were rolled back.

The validation uncovered one Supabase-relevant defect and one API gap. Session revocation
could fail when the application host clock lagged the PostgreSQL clock; the auth service
now writes revocation timestamps using the database clock, with a regression test. There
is no application-update endpoint in the current API, so that requested workflow could
not be validated. Existing-user password verification also remains unverified because
no existing user's password was supplied; password hashes were not reset or inspected.

## Database integrity and runtime target

The active runtime URL connected to Supabase PostgreSQL **17.11**. A read-only
repeatable-read snapshot after validation confirmed revision **20261003_0003**, **28
application tables**, and **312 rows**. The migration baseline was 280 rows. The 32-row
difference is entirely in `audit_events` as `AUTH_RATE` records generated by validation
requests. The following migrated business/authentication tables retained their baseline
counts: `users` 2, `auth_sessions` 29, `loan_applications` 8, and `predictions` 8. No test
user, test application, or test prediction remained. The existing application data was
read-only during the snapshot. These added rate-limit audit rows are retained as an audit
trail and were not deleted.

The runtime session and pooler connections succeeded. The auth/application API smoke
completed database-backed reads and writes without a pool timeout or SQLAlchemy error
after the clock fix. The full test suite uses an isolated disposable local PostgreSQL
test database; it was deliberately not pointed at the populated Supabase database because
its fixtures truncate tables and apply schema changes. The backend's active connection
was verified as Supabase; no local PostgreSQL dependency was required for the live API
smoke. Local PostgreSQL remains available as the preserved source copy.

## Supabase-specific fix

Initially, refresh/logout returned 503 because `ck_auth_sessions_revocation_time` rejected
a revocation timestamp generated by an application clock that lagged Supabase's database
clock. The auth service now obtains the persisted revocation time from PostgreSQL's
`clock_timestamp()` for refresh rotation and family revocation. Token expiry, token
contents, session rules, and API contracts are unchanged. A regression test deliberately
sets the application clock behind PostgreSQL and verifies rotation succeeds.

## Failures and remaining validation

1. Add or explicitly exclude an application update workflow. Current API supports create,
   list, detail, result, and history, but no update operation.
2. If confirmation of migrated-user password compatibility is required, perform a login
   using a known test user's existing credentials through the normal login UI/API. Do not
   share or record the password in this report.
3. Resolve the browser suite's five dark-theme color expectations or update the tests to
   validate the intended accessible dark-theme colors. Re-run the browser-driven auth and
   application workflow with the normal runtime server after that.
4. The 32 `AUTH_RATE` audit rows are persistent side effects of validation requests. They
   are expected audit records; no application/user/session/prediction records were added.

No model artifacts were loaded for training or changed. No migrations were run. Existing
API contracts, prediction behavior, and authentication policy remain unchanged except for
using the database clock when persisting revocation timestamps.
